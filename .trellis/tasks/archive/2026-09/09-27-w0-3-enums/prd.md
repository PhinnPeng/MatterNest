# W0-3 枚举 E01–E37 落地与 CHECK 一致性机制

> 权威源：`docs/PRD-phase1-enums-and-schemas.md`（B6 定稿 v3，全表 37 行、34 项真实取值）。
> 票面出处：落地方案 §3 M0「W0-3 … 审（这条错了后面全错）」。

## 为什么它是 M0 的闸门

技术选型 §13.5 禁令②③④ 全部关于"DB 与代码是否同步"，而枚举是**唯一一处前后端 + DB 三方共享的取值集合**：
状态机、规则引擎、通知、审计动作、DTO 校验都读它。做成两份实现（前端一份字典、DB 一份 CHECK）
就会漂移，且漂移表现为"配置页能选但后端拒绝"或"历史行违反约束"这类上线才炸的错。

## 范围

1. `src/shared/enums/` 七份文件，按枚举表 §5.1 的分册：`targets / status / business / notify / auth / audit / automation`。
   每项**同时导出**：TS 联合类型、值数组（顺序即 DDL 里的顺序）、中文名字典。
2. `index.ts` 汇总成 `ENUM_REGISTRY`：每条带 `id`（E01…E37）、出处、值数组、中文名，以及
   （若该值域进了 DB）它对应的**迁移 CHECK 约束名**。
3. **通用** CHECK↔值数组一致性测试（放在服务端层，不放 `src/shared` —— 禁令① 禁止 shared 用 `node:fs`）：
   双向比对：注册表声明的约束必须在迁移里存在且集合相等；迁移里出现的 `IN (…) CHECK` 必须被注册表认领。
4. 覆盖性测试：注册表必须覆盖 E01–E37 全 37 行（含 3 行"非枚举"占位），漏一条即红。

## 票面没写清、本票顺带裁定的三件事

- **§5.1 的分册表没给 E02/E04/E05/E06/E07/E10/E11/E37 归属**（只列了 E03/E09/E12–E22/E26–E28/E23–E32/E34–E36）。
  裁定：E02/E04/E05 进 `targets.ts`（同属"主体与关系"），E06/E07/E10/E11 随其值域来源进 `business.ts` / `status.ts`，E37 进 `auth.ts`。
- **`host_type` 在 E08 与 E10 两处登记且取值完全相同** → 只允许一份实现：值定义在 `targets.ts`，`status.ts` 引用。
  否则"改了 E08 忘了 E10"就是本票要防的那种漂移。
- **中文名的出处**：枚举表只给了一部分（E12/E13/E14/E15/E16/E19/E26 等）。其余按权限草案 §1/§2.2、
  修订稿 §3.2 的原词取，**不自行造词**；确实没有权威叫法的，在文件里注明"文档未给中文名"。

## 验收标准

- [ ] 七份文件 + `index.ts` 落地；`pnpm verify` 全绿（禁令① 的 lint 守卫仍生效）。
- [ ] 值数组与枚举表逐字一致：脚本比对 37 行全覆盖，无漏项、无多值、无改名。
- [ ] 一致性测试双向可红：注册表里删一条 ⇒ 红；迁移里改一个 CHECK 值 ⇒ 红（两条都实跑）。
- [ ] 已进 DB 的值域（当前只有 `status_config` 的 E08/E09）由迁移 CHECK 守；其余标记为"待建表"，
      不假装已落地。
- [ ] 回写：枚举表 §5.1（分册归属与 host_type 单实现）、落地方案 W0-3 状态、spec 的枚举节、CHANGELOG、journal。

## 非目标

不做配置表 CRUD、不给 `*_config` 建表（属 W1-2/W1-3）、不生成 OpenAPI（W1-7）、
不引入 codegen 管线（枚举表 §5.1 已明确裁定"手写 CHECK + 一条一致性测试"，本票遵从而不推翻）。
