## Problem Statement

这套系统今天**已经能跑**——案件、事项、当事人、转案件、通知、权限、导出、批量导入都在，
`pnpm verify:all` 单命令可全绿。坏掉的不是功能，是**外观与实现各说各话**：

1. **设计已经定稿，但只活在原型里。** 一轮完整的视觉重构产出了 31 页原型 + 一套令牌
   （`.impeccable/mocks/pages/canon.css`，44 个色 + 组件类）＋ 一份契约（`DESIGN.md`）＋
   一份逐页施工规格（`canon-spec.md`）。而 `src/` 用的还是上一版：主色 `#2f5fe0`（定稿是
   `#2563EB`）、纸色 `#f7f8fa`（定稿是 `#F5F6F8`）、导航 8 项（定稿是 3 组 9 项）。
   **两套视觉系统同仓并存，任何一处改动都要问"改的是哪一套"。**

2. **深色内容区在代码里被一条实现裁定禁掉了。** `theme/antd.ts` 现在是
   `algorithm: antdTheme.defaultAlgorithm` 钉死，注释写着「明暗只用亮色 … 深色内容区没需求也没有验收（P1-17）」。
   而原型已经出了全部 31 页的深色版，且**深色版是脚本从浅色版复制 + 加 `class="dark"` 生成的**
   ——即令牌体系本来就为深色准备好了。今天是靠一条注释把它关在门外。

3. **内容区的"空白"是设计缺陷而不是数据问题。** 已实测：角色权限页在 1440×900 下
   内容只到半屏就停（51%–64% 空白），原因是 `.page` 不参与高度分配。定稿版已用
   「逐层接力的 flex/grid 传递」修好（4% 空白，即 40px 的页底 padding），但这条修法在原型里，
   没进 `src/`。

4. **有三个功能在界面上没有落点。** 角色权限页（`/roles`）**路由根本不存在**；
   功能配置是 149 行的只读字典页（14 个细项里一个都改不了，也没有编辑入口）；
   批量导入（MATT-67 已交付接口、模板、报告、幂等）**藏在系统组一个独立页里**，
   用户不会去那里找它。

5. **「我收藏的」这个词与它的落点都不对。** 菜单里叫「我收藏的」、`/watch` 独立占一格；
   而定稿的语义是**「我关注的」**（`favorite` 与 `follow` 是 `mn_user_watch` 的两面，
   ADR-0003 已定），且它属于**个人的**入口，应该收进身份区而不是与业务实体并列。

**合成一句**：功能都在，但用户看到的那一层是上一版；定稿已经验收过一轮，
现在缺的是把它**转写进代码**，并在三处补上真正的落点。

## Solution

把 canon 原型**逐页转写进 `src/`**，同时补齐三处缺落点。分三批：

- **批次一 · 地基（令牌与外壳）**：`canon.css` 的 44 个色值转写进 `theme/brand.ts`
  （明暗两组同键名），`theme/antd.ts` 做 token 映射并让 `algorithm` 可切，
  `globals.css` 那三处写死的色收敛成变量，导航改成 3 组 9 项，
  内容区撑满视口的传递链落到真实布局，深色成为可切换的一等外观（ADR-0006）。
- **批次二 · 页面迁移**：把 31 页原型逐个对到 14 个真实路由（含新建/成功态弹层、
  14 个配置细项页、主从布局的角色权限页），**行为不变、只换视觉层**。
- **批次三 · 新接口与新交互**：新增只读 `/api/roles`；新增 `/api/config/[kind]` 的 CRUD；
  批量导入改成案件页/事项页内弹层（含数据预查看与服务端 `?dryRun=1` 预检）；
  「我收藏的」改名「我关注的」并把入口移进身份区。

三批是**纵向切片**，每批独自可演示、可验收：批次一落完，页面在明暗两版下都跑；
批次二落完，逐页与原型可逐像素比对；批次三落完，三个功能有了真实落点。

## User Stories

### 视觉与外观

1. As a **法务经办人**, I want 整套界面的主色与定稿一致（`#2563EB`）, so that 我看到的界面与评审过的原型是同一个东西，而不是两个版本。
2. As a **长时间读案卷的经办人**, I want 能切到深色内容区（不只是深色导航壳）, so that 夜里或连续读几十分钟时不必盯着一整屏亮白。
3. As a **看到同事发来的截图的人**, I want 我这边打开同一页也是同样外观, so that "我这边没有这个按钮"这类对话不会因为主题不同而反复发生。
4. As a **第一次打开系统的人**, I want 外观切换后刷新页面不闪回亮色, so that 首帧不会白闪一下再变深——那看起来像页面出错。
5. As a **键盘用户**, I want 外观切换控件能 Tab 到、能回车触发, so that 不必用鼠标才能换主题。
6. As a **色觉障碍用户**, I want 状态与期限不只靠颜色区分（点径 + 词）, so that "逾期"这类关键判断我读得出来。
7. As a **读屏用户**, I want 每页的标题层级是 h1 → h2 → h3 不跳级, so that 按标题跳转时能听出页面结构。

### 页容器与布局

8. As a **在 1440×900 上看页的人**, I want 内容区与左导航同底（空白落在卡片内部而不是页面底部）, so that 界面看起来是完整的一屏，而不是"半屏内容 + 半屏背景"。
9. As a **看数据少的列表页的人**, I want 表格行高恒定 40px、余量留在表格下方, so that 4 行数据不会被摊成每行 180px。
10. As a **看角色权限页的人**, I want 左侧角色列表与右侧内容区等高, so that 选中任何一个角色时右栏底部都不悬空（5 个角色都一样，将来加到 6 个也自适应）。
11. As a **看功能配置页的人**, I want 所有功能卡片等高（1 条细项的卡与 5 条的卡同高）, so that 卡片网格是齐的，而不是参差不齐。
12. As a **在窄屏上看功能配置页的人**, I want 卡片横向最多 5 张、放不下就往下挤, so that 每张卡里那几条细项名还是完整可读的。

### 导航与身份

13. As a **用户**, I want 导航是 3 组 9 项（概要 / 业务 / 系统）, so that 我能按职责找到入口，而不是猜"配置字典"和"用户与角色"为什么挤在一起。
14. As a **用户**, I want 当前所在页在导航里高亮, so that 我知道自己在哪。
15. As a **用户**, I want 我的身份与「我关注的」收在侧栏底部的身份区里, so that 个人的入口不占业务实体的位置。
16. As a **用户**, I want 点开身份区能看到「我关注的」与「退出登录」, so that 这两个"我的"动作在同一个地方。

### 角色权限页（新建）

17. As a **系统管理员**, I want 有一个只读的角色权限页, so that 我能看见 5 个内置角色各能看见什么、能做什么。
18. As a **系统管理员**, I want 每个角色列出它的数据范围（全公司 / 我参与的 / 我承办的）与四项特权（撤销归档 / 明文导出 / 管理账号 / 管理配置）, so that "为什么他能撤销归档我不能"有一个可查的答案。
19. As a **系统管理员**, I want 每个角色列出持有人数与成员清单, so that 我知道这个角色现在谁在用。
20. As a **系统管理员**, I want 成员变更处给一个指向用户管理页的链接, so that 我知道改人要去哪做，而不是在本页找编辑按钮。
21. As a **系统管理员**, I want 这个页明写"只读", so that 我不会找一圈"为什么改不了"。

### 功能配置（14 个细项）

22. As a **运营/管理员**, I want 功能配置入口按业务分组排列（事项 / 案件 / 当事人 / 风险 / 通知）, so that 我按"这是哪一类"就能找到要改的那一项。
23. As a **运营/管理员**, I want 案件状态、事项状态、风险等级、标签、费用项目这 5 项能真正增删改与启停, so that 运营改动不必等一次发版。
24. As a **运营/管理员**, I want 改动命名（如把"审理中"改成别的显示名）之后列表、报表、下拉一起变, so that 显示名只有一份。
25. As a **运营/管理员**, I want 7 个闭集枚举项（案件类型 / 案件程序 / 当事人类型 / 证件类型 / 诉讼地位 / 事项类型 / 节点状态）明确标成"改动要走迁移", so that 我不必一条条试"为什么这个改不了"。
26. As a **运营/管理员**, I want 新增与编辑走弹层（页面上不留常驻表单卡）, so that 列表本身不被表单挤走。
27. As a **运营/管理员**, I want 编辑弹层的字段按该页语义给（状态页多"语义"、标签页多"颜色"与"适用"、风险等级多"颜色"）, so that 每一页只问该问的东西。
28. As a **运营/管理员**, I want 每一页至少有一行是"停用"状态, so that 停用态是可见的、可恢复的，而不是一个隐藏能力。
29. As a **运营/管理员**, I want 停用一个被规则引用的状态时被明确拒绝, so that 我不会把正在跑的规则改坏。

### 批量导入

30. As a **导入历史台账的经办人**, I want 在案件列表页直接点开批量导入弹层, so that 我不必先找到系统设置里的那个独立页。
31. As a **在事项列表页导入的人**, I want 弹层里类型已被本页锁定（事项页导事项、案件页导案件）, so that 我不会选错模板导错表。
32. As a **上传文件的人**, I want 提交前先看到"这份文件会导入多少行、哪几行有问题", so that 我不会把一份表头写错的文件直接导进去。
33. As a **上传文件的人**, I want 预检与服务端用同一套判定, so that 预查看说能导的行，真的导得进去。
34. As a **上传文件的人**, I want 导入结果里"已导入 / 未导入"两个数同屏, so that 我一眼知道这次到底进了多少。
35. As a **上传文件的人**, I want 逐行错误原因看得见、完整清单可下载, so that 我能改完重传而不是全部重来。
36. As a **上传文件的人**, I want 三张模板（事项 / 案件 / 当事人）在弹层里可下载, so that "怎么填"当场就有答案。
37. As a **重传同一份文件的人**, I want 系统认出这是同文件重放并告诉我, so that 我不会以为"导了两遍"。

### 关注（原「我收藏的」）

38. As a **用户**, I want 菜单里叫「我关注的」而不是「我收藏的」, so that 这个词与系统的实际语义（关注 = 由我 star 建立、会收到状态与评论通知）一致。
39. As a **用户**, I want 「我关注的」在身份区点开就能到, so that 我不必在业务实体里找它。

### 一致性（跨批）

40. As a **下一个改这份代码的人**, I want `DESIGN.md` 与 `brand.ts` 逐值同源、且有测试守着, so that 我不会改了契约忘了实现（或反过来）。
41. As a **下一个改这份代码的人**, I want 一节 `canon-spec.md` 能对上一个真实路由, so that 迁移进度不靠记忆。
42. As a **复核这次重构的人**, I want 31 页 × 明暗两版都有对比度实测, so that "深色没验收"这句话不再成立。
43. As a **复核这次重构的人**, I want 逐页与原型可比对（截图或实测数字）, so that 验收不靠"看着像"。

## Implementation Decisions

### 令牌与主题（批次一）

- **`theme/brand.ts` 从"一组色"改为"明暗两组同名色"**：把 `canon.css` 的 `:root`（44 色）
  与 `body.dark`（同键）两套值都收进来，键集合**必须相等**——`brand.spec.ts` 是这道闸门
  （禁令⑦ 的另一半：一个色只定义一次）。
- **`theme/antd.ts` 让 `algorithm` 可切**（`defaultAlgorithm` ↔ `darkAlgorithm`），
  并由 `ConfigProvider` 传入；`theme.components.*` 的尺寸刻度不因此改变。
- **外观状态放 `localStorage`，首帧不闪**：SSR 时先按亮色渲染，客户端读一次已存值。
  实现要点是**在 `<head>` 里同步注入**（不能等 hydration），否则会看到白闪。
- **`globals.css` 的三处写死色（纸色底、`::selection`、滚动条）收敛成 CSS 变量**，
  由一处注入明暗两值；此前靠"两处一起改"的注释约束，深色进来后从两处变四处。
- **P1-17 撤销**，落 `docs/adr/0006-dark-mode-first-class.md`，
  并在 `tech-stack-decision.md` §13.5 的 P1-17 就地加一行指回该 ADR（旧文字保留、标注被谁取代，
  照 P1-18 作废的写法）。
- **导航改 3 组 9 项**：概要（工作台 / 我关注的 / 通知）、业务（案件 / 事项 / 当事人 / 已归档）、
  系统（功能配置 / 用户管理 / 角色权限）。**批量导入从导航移除**（见批次三）。
- **`/config` 这个只读字典页的去留**：**保留**，但它改名为「功能配置」入口页
  （5 张卡片指向 14 个细项），原先的"闭集枚举改不得"说明搬进每个细项页的显式标注里
  （见下）。它**不是** P11/P17 的替身。
- **内容区撑满视口的传递链**照 `DESIGN.md` 的 Layout 节逐条落：
  `.page` → 末元素（`.card` / `.stack` / `.master`）→ 卡内主体；
  判据是「任一页在 1440×900 下内容底边与视口底差 ≤40px」。**表格行高不参与拉伸**。
  ⚠ 两条已知坑写进代码注释：`.master` / `.split` 是 grid，不许写 `flex-direction`；
  功能配置的卡片网格必须是最后一批元素之外的**独立容器**，不能被 `:last-child` 追上拉高。

### 页面迁移（批次二）

- **逐页对表**照 `canon-spec.md` 的页面清单（01–31）逐条落，`DESIGN.md` 是视觉契约。
  迁移期间 `DESIGN.md` 顶部那张「落地状态（迁移中）」表**逐批更新**，搬完一批删一批行。
- **行为零改动**：这一批**不新增业务接口、不改服务层口径**。唯一的例外是批次三列出的三处。
- **主从等高**（角色权限页）照 `research-master-detail-equal-height.md` 的结论：
  不写 `align-items:start`、右栏 wrapper 是 flex 列、pane 内末张卡 `flex:1 1 auto`。
  **不写死高度**——加到第 6 个角色要自适应。
- **标题层级不跳级**：顶栏页名 h1 → 卡片头 h2 → 嵌套 h3。改标签不动视觉
  （`.card-h` 对 h2/h3 同貌）。
- **列宽预算 ≤1100 @1366**：表格一律显式列宽 + 可伸缩列补省略号。

### 新接口（批次三）

- **`GET /api/roles`（只读，新增）**：返回 5 个角色及其 `code` / `name` / `dataScope` /
  四项特权 / 持有人数与成员摘要。**数据范围标签用 `DATA_SCOPE_LABELS`，不在页面里抄第二份**。
  权限门：登录即可读（与 `/api/users` 的"能看见才能管"不同——**角色定义不是人的隐私**），
  但成员清单部分按 `/api/users` 同一道门（`canManageUser`），看不到就只给计数。
  ⚠ 这条权限口径是本批**唯一一处需要人点头**的裁定，见 Further Notes。
- **`/api/config/[kind]`（CRUD，新增）**：`kind` 是**实体的枚举**（不是自由字符串），
  第一版只覆盖 5 个可写细项中映射到库表的那些：`matter-status` / `risk-status` /
  `risk-level` / `tag` / `expense-item`。请求与响应形状一律过
  `shared/schema/config.ts`（**新增**，前后端同一份，禁令⑧）。
  写门是 `canManageConfig`。
- **7 个闭集枚举项、2 个无实体项**（节点通知状态 / 节点通知时间）**不建 CRUD 接口**：
  闭集枚举改动要走迁移；后两项在库里没有承载（通知规则的存在与参数现在由
  `mn_automation_rule` 的 seed 决定，"哪些节点状态要通知"这件事没有一张可编辑的表）。
  三个都在页面上**明写为什么改不了**，不摆禁用按钮。
- **`mn_node_type_config` 有可写表但不在 14 细项里**（它是 PRD 的 P15）：本批**不做页面**，
  在 Further Notes 登记为已知缺口，避免它变成"看着像做了"。

### 批量导入改造（批次三）

- **原型三变体的定稿 = 变体 C**（用户已选）。实现里**删掉 A / B 两条分支与 `?variant=` 选择器**——
  那是约 200 行"待定稿"的脚手架，留着会让人以为还要选。
- **入口移到案件页与事项页的页头按钮**，弹层形式（与新建案件弹层同形）。
  **类型由入口页锁定**：案件页 → `matter`，事项页 → `risk_matter`，弹层里不给类型选择器。
- **`/config/import` 独立页保留**，但降级为「最近导入批次 + 报告找回」——用户关掉弹层之后，
  报告还得有个地址能回来拿。导航里不再有它，从弹层成功态的链接进。
- **新增服务端预检 `?dryRun=1`（同一个 `POST /api/import`）**：走与真导入**完全同一条解析与校验路径**，
  只跳过写库，返回同样的 `ImportSummary` 形状。这样"预查看说能导的行真的导得进去"
  不是一句约定，是同一个实现跑了两次。
  ⚠ 幂等判定（内容键）在 dry-run 里**照常参与**，否则预检会说"能导"而真导时全被跳过。
- **数据预查看的呈现**：解析出的行**只显示前 N 行**（上限与报告的 `SUMMARY_ISSUE_LIMIT` 同源），
  并给出「共 X 行 / 将导入 Y / 有问题 Z」三个数——**这三个数必须同屏**，与 P14 的核心信息一致。
- **模板下载**在弹层内可直接触达（复用既有 `GET /api/import/templates`）。

## Testing Decisions

**好测试的判据**：只断言**外部行为**，不断言实现细节。三条具体化：

1. **新接口测形状与权限，不测 SQL**。`/api/roles` 的测试断言"5 个角色都在、每个带着范围与特权、
   非 `canManageUser` 的人拿到的是计数而不是成员清单"；`/api/config/[kind]` 断言
   "非 `canManageConfig` 是 403、闭集枚举 kind 是 400、合法 kind 能增改启停"。
   **不断言服务层怎么查的**——那会随迁移重写而红，而迁移不改行为。
2. **令牌测试测"同源"，不测"好看"**。`brand.spec.ts` 断言明暗两组键集合相等、且每个键
   在 `canon.css` 两侧能找到同值。**它不判断颜色好不好看**——那是人眼与对比度脚本的事。
3. **视觉冒烟测"可读性底线"，不测像素**。跑对比度（WCAG AA：正文 4.5:1、UI 组件 3:1），
   不断言"某元素在 x=1240"。像素断言会在每次有意调整布局时红，而布局调整正是这一批的目的。

**被测模块**：

| 层 | 模块 | 断言什么 | 先前实现（prior art） |
|---|---|---|---|
| 新接口 | `api/roles` | 角色形状 / 权限分档 | `api/matters/export/route.spec.ts` |
| 新接口 | `api/config/[kind]` | kind 值域 / 写门 / 启停 | `api/risk-matters/[id]/unconvert/route.spec.ts`（含 403 与非法入参分档） |
| 新 schema | `shared/schema/config.ts` | 前后端同一份形状 | `shared/schema/import.spec.ts` |
| 令牌契约 | `theme/brand.spec.ts`（**扩展**） | 明暗同键 + 与 canon 同值 | 现有 `brand.spec.ts` |
| 视觉 | `agent-work/smoke-visual.mjs`（**新增**） | 31 页 × 2 版对比度 | `agent-work/_chk/contrast-all.mjs`（已有，接进冒烟族） |

**不测的**：页面布局、卡片高度、导航高亮、弹层开合。这些由 `agent-work/_chk/` 下的一次性
测量脚本按批核对（`verify-fill-all.mjs` / `verify-equalheight.mjs` / `check-headings.mjs` 已有），
**它们不是 `verify` 门禁**——理由与 `branches:merged` 同源：判据依赖本地运行态的东西不该挂 CI。
