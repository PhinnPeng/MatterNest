# 事项补结构化进展表；「处置记录」退回评论对话

2026-10-23 裁定（迁移 `0021_risk_matter_progress.sql`）。至此 `mn_matter_progress` 与 `mn_risk_matter_progress` 是同构一对，由 schema 的 `progressTable(host)` 工厂产出；`enum-check.spec.ts` 的 `ISO_PAIRS` 第五对逐列看守。事项详情页新增「进展」页签，完成节点后可顺手写一条（可跳过，可挂当前节点）。「处置记录」不再承担办理过程，它只是**评论对话**。

## 为什么改（原口径不够用）

修订稿 §6.3 原本明写「不给事项加 `risk_matter_progress`，一件事项的办理过程走评论时间线」。落地后出现两个问题：

- **评论与进展是两种东西，混在一条时间线里读不出来**。评论是讨论（@同事、附件、追问），进展是"哪一天、以什么方式、推进到哪一步、下一步做什么"的结构化台账。事项列表要按"最近进展"扫读、导出要按"类型/日期/内容/下一步"成段，这些都无法从评论正文里可靠还原。
- **案件与事项在这一点上不对称，但业务上并不对称**：事项是台账，同样需要"什么时候做了什么"的可回看记录。原口径让事项只能靠正文自由书写，同一团队在案件侧养成结构化习惯、到事项侧反而没有入口。

## Considered Options

- **继续只靠评论**（原口径）——被否：上面两条都无解，且以后再加表要重写一次口径。
- **复用评论表加 `comment_kind` 区分进展**——被否：评论的字段（逐层回复、@提及分段、附件）与进展的字段（类型、发生日期、下一步、节点外键）几乎没有交集，塞进一张表会让两侧都带一堆 NULL；而"进展挂节点"需要真外键，评论的 `target_id` 是多态的，给不了。
- **只做一张 `matter_progress`，事项用 `host_type` 多态**——被否：与既有拆表决策（§1.0.2）相反；同构两张 + 工厂函数已经证明能守住漂移（节点/费用/人员/当事人四对）。

## 边界（这次特意没做的事）

- **不接规则 4「30 天无更新」**。`last_progress_at` 加在 `mn_risk_matter` 上，只作详情页读数与"最近进展"显示；IQ-9 / Q37 的提醒面仍然只扫案件。要扩面是另一次裁定，届时列已经在了。
- **只做创建，不做编辑/删除**。案件侧的进展端点也只有 `POST`（`PROGRESS_UPDATED/DELETED` 至今是没有写入点的枚举占位）。事项侧单方面补编辑会让两条线重新分叉；要补就两侧同一批补。
- **冻结门保留**：已转案件的事项写进展返回 `422 frozen`（ADR 0005 的"冻结覆盖全部业务事实"）；已归档返回 `403`。读到已有进展不受影响——冻结挡的是新写入，不是回看。

## Consequences

- 审计新增 `target_type = 'risk_matter_progress'`（E03 扩域，迁移 0021 重建 `ck_mn_activity_target_type`）；`TARGET_TYPE_LABELS` 加「事项进展」。
- 事项列表/详情、整卷导出的「事项进展」段、演示种子（8301 两条）都走同一份数据。
- 前端 `progress-panel.tsx` 由案件与事项共用；两份各写一份的失败形态是"一侧改了校验、另一侧还是旧的"，而那不会报错（与 `node-dialog.tsx` 同一理由）。
- 文档：`docs/PRD-phase1-design-revision-r1.md` §1.5 / §6.3 的原口径在此标记为已被本 ADR 取代。
