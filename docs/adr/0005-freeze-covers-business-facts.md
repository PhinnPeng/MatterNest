# 冻结覆盖全部业务事实，协作面与标签刻意豁免；硬期限只在案件侧调

事项转过案件即冻结（2026-10-14 裁定，实现 `496da50`，判据 `services/risks.ts` 的 `isRiskFrozen` = `conversion_status === 1`）。三张遗留票（MATT-80/81/82）于 2026-10-16 经 MATT-89 一并裁定：**冻结覆盖节点、当事人、软删**（此前它们不拒冻结）；**标签允许加、评论/关注人/追加转案件保持开放**——这三类是**刻意豁免**，不是漏加的门；**转案件后不可撤销维持原判**，三道前置检查（进展/非预设节点/费用）降级为备用防线。

## 为什么是这个形状（而不是别的）

- **一条主线**：事项是台账、案件是战场（IQ-5/6 的不对称裁定）。转案件 = 业务事实移交给案件，此后以案件侧为准。所以凡**改变业务事实**的路径都要冻结；凡**协作与分类**的路径都不算改变事实，保持开放。
- **节点为什么必须锁**（不是可选项）：事项的节点常是硬期限（举证期、开庭日），冻结前事项侧仍可改，而期限的实际推进已在案件侧——**改错了没人会发现**，这是三张票里唯一「无人察觉即造成损害」的形态。紧急调整期限走**案件侧**，不回头改台账。
- **归档与冻结的分界**：归档更严（只读终态，评论尚且允许——基线 1.7）。若冻结把评论/关注也锁了，就会出现「冻结比归档更严」，与既有裁定冲突。所以协作面开放是**一致性要求**，不只是方便。
- **撤销谓词为什么不放宽**（MATT-81 选项②被否）：放宽成「案件有下游投入才不可撤」会推翻「冻结按已转案件算」这条已验收裁定，要动 §7.4；而现状的痛只是文案不清，补一句「这是规则不是故障」就够了。

## Considered Options

- 节点只读（可看不改）——被否：与完全锁住行为相同，只是多造一个拒绝原因；期限本来就该去案件侧改。
- 节点保持开放 + 界面说明——被否：留着静默改期限的洞，靠文案兜不住。
- 撤销端点直接删——被否：删一条已验收能力换不来任何清晰度，frozen 拒绝语义留着正好向用户交代规则。

## Consequences

- 施工 = 一个批次挂 M3（MATT-80/81/82）：`addRiskNode`/`setRiskNodeStatus`/`appendRiskParties`/`removeRiskParty`/`deleteRiskMatter` 补 `isRiskFrozen` 门；`batchTagRiskMatters` 处要写注释标明「豁免是刻意的」；`risks.spec.ts:315-338` 那组「当前不锁」断言同步翻转，**先反向红一次**。
- 软删冻结的连带效果：事项被 N 个案件引用期间不会断源，案件详情页「来源事项卡」不存在显示空态的问题。
- 「豁免」清单从此有约束力：以后想给评论/标签/追加转案件补冻结门的人，先回来看这条 ADR。
