# 深色内容区升为一等外观：撤销「一期只要亮色」（P1-17）

**P1-17**（技术选型 §13.5 时期的一条实现裁定）写的是：

> 明暗只用亮色：一期是内网宽屏 PC，深色内容区没需求也没有验收。

这条裁定在 2026-10-17 的视觉重构里被**撤销**。它当时的推理没有错——"内网宽屏 PC"是真的，"没有验收"也是真的——错的是它把**「没有验收」读成了「不需要」**。二者的差别在这一次重构里被具体化了：

1. **深色不是一种"主题选项"，它是长时读表场景的默认诉求。** 这套系统的核心动作是盯着案卷与节点期限读几十分钟，而交付形态是一块内网 PC 屏。亮色纸底（`#F5F6F8`）在这个场景下是**可用的**，但把它当成唯一外观，等于把"夜里看、屏前坐满一天"这类真实使用排除在设计之外。裁定当时没有任何一处记录说"我们问过用户，他们说不要深色"。

2. **"没有验收"是可以补的，不是不可补的。** 原裁定把"无法验收"当成了"不必实现"的理由。实测上这不成立：这一轮已经建了两条可机检的门槛——
   - `agent-work/_chk/token-contrast.mjs`：令牌配对的对比度；
   - `agent-work/_chk/contrast-all.mjs`：**全站渲染实测**对比度。
   两条都在最差的浅色面（纸色）与深色面（`body.dark` 的导航/内容底）上各跑一遍。31 页 × 明暗两版，0 失败。也就是说"深色能不能验收"这个问题，答案已经变成"能，而且是机械的"。

3. **令牌体系已经天然支持深色。** 全部 44 个色值都在 `canon.css` 的 `:root` 与 `body.dark` 两处成对定义，没有任何一处业务样式写死颜色。原裁定若继续生效，就得在实现里**主动把 `body.dark` 这一半删掉**——那是比保留它更多的动作，而且删掉之后 `brand.ts` 的单源约束反而更难维持（下一段）。

## 决定

**深色内容区（不只是深色导航壳）成为一等外观。** 从 `theme/antd.ts` 起落：

- `algorithm` 不再是钉死的 `defaultAlgorithm`，而要能随外观在 `defaultAlgorithm` / `darkAlgorithm` 之间切换；
- `brand.ts` 不再只有一组亮色常量——它要持有**明暗两组同名的语义令牌**（44 个色的两套值），与 `canon.css` 的 `:root` / `body.dark` 逐值同源；
- 切换控件落在导航底部的身份区（`navfoot` 的位置，原型已是 `.modesw`）；
- 外观是**用户可见的一等状态**，不是开发者开关：它进 `localStorage`，首帧要避免闪烁。

## Consequences

- **`brand.ts` 从"一组色"变成"两组同名色"。** `brand.spec.ts` 是这道闸门（禁令⑦：一个色只定义一次）：它要断言明暗两组**键集合相等**，且每个键在 `canon.css` 两侧都能找到同值。少一个键、两组键名不一致，测试就红。
- **`globals.css` 里那三处写死的色（纸色底、`::selection`、滚动条）必须跟着走。** 它们是 CSS 侧 import 不到 TS 常量的地方，此前靠"两处一起改"这句注释约束。深色进来之后这条约束从"两处"变成"四处"（`globals.css` 的明色 + 暗色），所以它们应当收敛成 CSS 变量，由一处注入。
- **对比度门禁从"可选"变成"必须跑两道"。** 只跑亮色等于让深色无声上线——而深色正是"没有验收"这句话的原始受害者。两道脚本进 `pnpm verify` 的候选清单（是否入 CI 链另议，`branches:merged` 那条区分同样适用）。
- **观感走查（MATT-30 / MATT-29）的范围随之扩大一倍。** 每一页要在明暗两版上都走过一遍，不只是亮版。
- **`docs/tech-stack-decision.md` §13.5 的 P1-17 条目不再是现行裁定。** 该处应加一行指回本 ADR，与 P1-18 作废（MATT-35）同一种做法——**旧文字保留、就地标注被谁取代**，不删改历史结论。
- 撤销的是"只要亮色"，**没有**撤销它的另一半判断：一期仍是**内网宽屏 PC**，不是移动端。深色与响应式是两件事，本 ADR 只碰前者。
