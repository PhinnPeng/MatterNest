## 候选 1 · 一条门禁覆盖本轮一半的机械错误

**Sever���**

`agent-work/smoke-*.mjs` 里 **21 处** `await call(...)` 把返回值丢掉（语句表达式）。
我只修了触发点那一处 —— 剩下 20 处是同样的形状，同样会在某天静默塌陷。

**为什么门禁抓不到**：`pnpm verify` 的五道里有 lint / typecheck / test / lint-guard /
anchors-check，**没有一道读 `agent-work/*.mjs` 的语义**。`anchors:check` 只从
`revred-*.mjs` 抽 needle 字面量，`lint-guard` 的 walk 只扫 `src/**`。

**建议**：`tools/lint-guard/check.mjs` 加第七道断言（或独立 `smoke-hygiene.mjs`
接进 `verify`）——

```
在 smoke-*.mjs 里，`await call(...)` 作为**独立语句**出现
  ⇒ 必须紧跟一条 ok(...)，或在同行/上一行有 // discard: <理由>
```

反向红很容易造：把某条 `const x = await call(...)` 改成 `await call(...)` 而不补
`ok`，断言必须红。

**为什么它划算**：一条正则覆盖错误 2；错误 1 的形状是同一类（**值被拿到了却没被
用**），同一道门可以顺手扫 `const [x] = await sql` 后面**没有**用到 `x.length`
或 `x.find` 的情形 —— 那就是恒假断言的形状。

⚠ **诚实的边界**：第 1 类（恒假断言）**语法上与正确写法同形**，正则只能扫
「拿到了却完全没用」，扫不出「用错了地方」。它能抓本轮这一条，抓不了全部。
这一类剩下的部分要靠评审。

## 候选 2 · 冒烟清场不该是共享库的隐式写入者

**Sever���**

清场连坐的后果不是「账号没删掉」，是**共享 dev 库被污染，而报错指不到来源**：
`db:check` C14 报「持有者 5 人，草案 §3：仅 1–2 人」——那句话完全看不出是冒烟
留下的。我为此手工清了 22 个账号（业务行要改挂真实 admin，不是置 null，因为
案件侧 `owner_id` 与 `mn_comment.author_id` 都是 NOT NULL）。

**已做**：`dropSmokeAccountsSafely` —— 逐个独立、失败收进返回值。
但**只有 `smoke-risk` 改用它**，因为其余 8 个单账号调用点**本来就各自包了
try/catch**（单账号场景防得住，只有多账号会连坐）。

**建议**（两者都要）：

```
① 把「冒烟跑完库必须干净」变成一条可跑的检查
   —— 一个 probe：跑完全组冒烟后跑，报残留账号数 / 孤儿业务行 / is_admin 持有者数
   —— 它现在是 db:check C14 兼这个职责，而 C14 的报错文案指不到来源

② 清场失败的退出码
   —— 现在清理失败只 console.log，脚本仍然 exit 0/1 按断言数走
   —— 清理失败应当**至少让 CI 看得见**（否则「跑过了」与「跑干净了」同形）
```

这一条是 `/retro` 说的「**机械失误变成确定性检查**」的教科书形态：
清场失败现在只被人眼看见，而人眼不看冒烟的清理输出。

## 候选 3 · 全组冒烟从未被当成一条命令跑过

> ✅ **已于同日落地**（`tools/run-smokes.mjs` + `pnpm smoke`）。
> 首次全组实跑：17 脚本 / 887 断言 / 退出码 0。

**Severity：高**

17 个脚本、887 条断言、共享一个 dev server 与共享库。**没有一条命令跑全组**
（`pnpm verify` 不含冒烟，因为冒烟要起 dev server）。

后果本轮实证：

```
④ smoke-improvements 读 process.env.BASE / 默认 3000
  而其余 17 个读 SMOKE_BASE / 3777
  ⇒ 起在非默认端口时它是全组唯一连不上的那个
  ⇒ 它从未被跑过（连不上就一直失败，但没人看）
```

一个**从不成功执行过的脚本**，躺在「全绿的冒烟目录」里，是最坏的一种状态 ——
它提供的是虚假覆盖。

**已落地**：

```
① tools/run-smokes.mjs + pnpm smoke
   自动发现 agent-work/smoke-*.mjs（新增脚本自动进队，不靠人记得）
   探活 → 串行跑 → 逐项超时（默认 180s，取自 smoke-batch 自带的 150s 看门狗
   加余量）→ 汇总表 → 任一失败/超时/起不来/未见汇总 ⇒ 退出码非 0
   --only <片段> 可单支跑
② 端口钉进 dev 脚本：`next dev --port 3777`
```

### ⚠ ② 这条修的是根因，不是症状

代理在实现时查出：**`smoke-improvements` 的端口问题与「根因」是同一件事**。

```
package.json 的 dev 是裸 `next dev`   ⇒ 默认 3000
next.config.ts 不设端口
.env 没有 PORT
17 个冒烟全部硬编码默认 3777         ⇒ 纯粹是口头约定
```

也就是说：按 README 的 `pnpm dev` 起起来，**`pnpm smoke` 会立刻全红**（探活失败），
而这不是冒烟的错，是两边对「dev 在哪个端口」的认知不一致。

第一轮我只改了脚本（统一到 `SMOKE_BASE`），**坑还留在那儿**。现在把端口钉进
`dev` 脚本 —— 按 `writing-for-agents` 的原则，**端口是环境自己的事**，
不该靠文档或人的记忆承载；钉进去之后，`3777` 这个数字不需要任何人记住。

**Severity: 中（但它放大了上面三条）**

核实结果：无 `.github/workflows`、无 `.husky`、无 `CODING_STANDARDS.md`。
`pnpm verify` 存在且很完整，但**只能靠人记得跑**。

**建议**（二选一，按成本）：


如果是，那该记成一个 wayfinder 票而不是「有空再说」。

## 候选 5 · 「声明了但没人执行」已有一道门，但形状只覆盖值集合

**Severity: 中**

本轮新加的 `enum-check` 写入点门禁（a781bf8）证明了这类检查**在本仓做得出来**。
但它只覆盖**值集合类**不变量（`IN (...)` —— 正则读得了）。

`docs/survey-missing-seams.md` 与 `docs/architecture-review` 同时指出**矩阵类**
不变量（哪些动作原因必填、哪些列变化不写日志）**零消费者**，因为没有可表达的形状
给扫描器。

`activity.ts:23` 的 `action: string` 是这类的成本证据：类型系统给出零 enforcement，
于是「动作必须合法」只能靠约 150 行手写词法分析器 + 16 条散文白名单去买。

**建议**：**先别加门禁**。正确顺序是

```
① 先把那六个常量变成真接口（被服务层真的查）
② 有消费者了，enum-check 的扫描器工作量可以大幅收缩，甚至退成一条类型断言
```

**先有消费者、后有门禁**，反了就是又一张零消费者的表 —— 那正是这六个常量自己的
处境。
