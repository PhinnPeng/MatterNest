## 1. 三档数据范围

按「我与这条记录的关系」分级。**不设"仅我创建的"第四档**——它只在存在"录入但不办理"这类分工时才有意义，第一期不假设，因而不留空转档位：

| 档 | code | 该档用户能看到的集合 |
|---|---|---|
| **L1** | `all` | 全所每一案件/事项 |
| **L2** | `participating` | 我承办的 ∪ 我协办的 ∪ 我被加为关注人的 ∪ 我创建的 |
| **L3** | `owned` | 我承办的 ∪ 我创建的（**不含**他人加给我的协办/关注） |

宽度：`L1 ⊃ L2 ⊃ L3`。**不设"仅我创建的"第四档**——它只在存在"录入但不办理"的分工时才有意义，第一期不留无判定内容的空转档位。

> 基线 1.3 与十 的「外部/访客 = 只读」第四档随 v3 一并作废，且**第一期不支持外部/访客账号**（2026-09-26 裁定，列 Out of Scope）：在"可见即可操作"下没有"能看不能改"的表达位。若将来要外部查阅，那是重新引入功能权限点的理由，须重开 §2.2 与 §10。

三条元规则：

1. **多角色取最宽并集**。
2. **可见即可操作**——不再有"能看不能改"的权限点区分。唯一例外是 §2.1 的 4 个特权开关与 §2.2 的两条归属护栏。
3. **默认拒绝**：无角色用户只能看到自己的通知与关注列表，业务表一律不可见；不可见资源一律 **404**（不返回 403——"这个案号存在但你不能看"在律所本身就是敏感信息）。

## 2. 内置角色（按功能机制划分）

角色名描述**这个角色在系统里做什么**，不描述使用者是什么岗位。岗位/职级到角色的映射属于部署时配置，不进设计，也不参与任何判定。

| 角色 code | 功能名 | 数据范围 | 特权开关 | 功能边界 |
|---|---|---|---|---|
| `sys_admin` | 系统管理 | **L3** | `manage_config` + `manage_user` | 只管配置与账号。范围刻意压到 L3，因此**看不到别人的案卷** |
| `full_admin` | 全局管理 | **L1** | `unarchive` + `read_plain` | 不可逆与敏感动作的唯一持有者；1–3 个账号 |
| `full_operator` | 全局经办 | **L1** | 无 | 看全所并正常办理，但撤销归档、明文查看都不行 |
| `joined_operator` | 参与经办 | **L2** | 无 | 主力角色 |
| `self_operator` | 承办经办 | **L3** | 无 | 最小业务角色，只能动自己承办或自己建的 |

> **`sys_admin` 的 L3 是这套模型的关键一处**：在"可见即可操作"下，数据范围**就是**读权限，没有独立的 `*:read` 权限点。所以"能管系统但不看案卷"这个诉求只能表达为 `scope=L3 + 系统特权`——功能与范围是两个正交轴，这也正是按功能而不是按岗位划分角色的理由。
>
> **多角色并集承担组合场景**：既要管系统又要能撤销归档的人，给他 `sys_admin` + `full_admin` 两个角色，靠"取最宽并集"生效，不新增第 6 个角色。
>
> 部署示例（**仅供配置参考，不是模型内容**）：主任/风控 → `full_admin`；合伙人 → `full_operator`；执业律师 → `joined_operator`；实习/助理 → `self_operator`；IT → `sys_admin`。

### 2.1 四个特权开关（挂在角色上）

| 开关 | 语义 | 哪个角色持有 |
|---|---|---|
| `can_unarchive` | 撤销归档（修订稿 §3.3 归档终态的唯一出口） | 仅 `full_admin` |
| `can_manage_config` | 5 类配置表（状态/节点类型/费用项目/等级/标签）增删改 | 仅 `sys_admin` |
| `can_manage_user` | 用户、角色、数据范围调整 | 仅 `sys_admin` |
| `can_read_plain` | 当事人证件号/手机号明文 + 明文导出（§7.3） | 仅 `full_admin` |

> **为什么只留这四个**：它们都是"影响别人或不可逆"的动作。其余业务动作（建案、改状态、加节点、录进展、报费用、评论、归档、转案件）都属于"我在范围内就能做"，拆成权限点只会增加配置负担而无隔离收益。
> 将来若确需细分，再加 `permission`/`role_permission` 是**加法变更**，不会返工现有设计——所以第一期不留位。

### 2.2 两条归属护栏（"可见即可操作"必须配的例外）

因为 §6 里"把某人加为关注人" = 授予其全部读写，所以不能允许参与人互相扩权：

1. **只有 `owner`（承办人）和具备 L1 数据范围的用户可以**：变更承办人、变更状态、归档、删除、增删协办/关注人。
2. **其他可见者**（协办人、关注人）可以：读写节点、进展、费用、评论、附件、自定义提醒。

即"能看就能写明细，但改归属和改状态要承办人本人"。这两条**硬编码在动作实现里，不配置化**——它们不是权限点，是"可见即可操作"这个简化能成立的前提。

> **未决一处（P0-6，待产品裁定）**：基线通篇有"编辑案件/事项字段"，但两条护栏只覆盖了"改承办人、改状态、归档、删除、增删参与人"，没写**主表业务字段**（名称、案由、金额、法院、描述…）归谁。建议口径：主表业务字段属护栏 2 的"明细读写"，协办与关注人可改；`owner_id` / `status` / 参与人三类归属字段属护栏 1。裁定前实现按建议口径走，但不得当作已定稿。

## 3. 模型（3 张表）

| 表 | 关键列 |
|---|---|
| `app_user` | id, username, name, is_enabled, **is_admin**, **token_version bigint**, **activation_status(`pending`/`active`, E37)**；**不带任何认证列**——凭据外挂 `app_user_credential`（本地密码，1:0..1）、`app_user_external_identity`（云之家 eid/openId，UK(provider, external_id)），会话表 `auth_session.auth_via` 记这次从哪条通道进来（技术选型 §3.4） |
| `role` | id, code, name, **data_scope 枚举(L1–L3)**, `can_unarchive` / `can_manage_config` / `can_manage_user` / `can_read_plain` 四布尔, is_builtin, is_enabled |
| `user_role` | (user_id, role_id) UK |

- **无 `department`、无 `matter.dept_id`、无 `permission`/`role_permission`**（v3 删除项）。
- 用户表**不留可空 dept_id 占位**（本轮已定）。若将来出现分所隔离需求，那是模型重写，不是补列——不为此预留。
- `is_admin` 独立于角色，是绕过范围的最后开关，仅 1–2 人，防止误删角色导致无人可管。
- **登录双通道不改变权限判定**（2026-09-26 裁定：云之家 + 本地密码，细节见技术选型 §3.4）：判定只看 `user_role.data_scope` + 特权 + 护栏，`auth_via` 只进审计。**云之家在职同步只写 `is_enabled`，不得把部门/岗位落库、不得参与任何谓词**——这是"第一期无组织维度"这条决策的守门处，通讯录一进来最容易顺手破。
- 离职回收是**安全边界而非便利功能**：`is_enabled=false` 必须同事务删 `auth_session` 并 `token_version++`，否则已吊销的会话在绝对过期前仍可读取全案卷。本地密码账号没有这条自动回收，所以密码通道能覆盖的账号要尽量少。
- 系统内部身份（`operator = SYSTEM`）**不建 `app_user` 行**，用常量 id，特权恒为假（§8）。

## 4. 范围谓词

```
visible(user, m) =
     user.is_admin
  OR scope = L1
  OR (scope = L3 AND (m.owner_id = :me OR m.created_by = :me))     -- 我承办 或 我创建
  OR (scope = L2 AND (m.owner_id = :me OR m.created_by = :me
        OR EXISTS (SELECT 1 FROM matter_staff s
                    WHERE s.matter_id = m.id AND s.user_id = :me))) -- 再加 协办/关注
```

外层恒定叠加：`AND NOT m.is_deleted AND (:include_archived OR NOT m.is_archived)`。

- 从属实体（节点 / 进展 / 费用 / staff 行 / 标签行 / 附件 / 评论 / 日志）**不自带范围**，一律先解析宿主再放行。入口给子资源 id 时必须先取宿主，禁止按 id 直查。
- 配置类 5 张表**不受范围限制**：全体登录用户可读（下拉要用），仅 `can_manage_config` 可写。给它们套范围会出现"别人建的标签我选不到"，属错误建模。
- 落地方式：显式 `ScopeResolver` 产出谓词 + Repository 强制入参。**不用** ORM 拦截器自动注入（改写 SQL 后索引不可控，且"哪条查询被注入了"无法静态审计）。PG RLS 列第二期。

防漏加谓词的两条机制（默认拒绝现在全靠这一层）：

1. 对宿主表的读必须经 `ScopedQuery` 构造，禁止裸表访问（仓储基类断言 + lint）。
2. §10 测试矩阵。

### 4.1 可见用户集（2026-09-26 收窄裁定新增）

§6 的"加参与人"动作自本轮起受一条新约束：**被加者必须落在操作者的可见用户集内**。在此之前 `is_enabled=true` 即可被加，等于任何登录用户都能把自己没见过的案卷开放给全所同事。

```
selectable(user, u) = user.is_admin OR scope = L1
                        ? (u.is_enabled)                                   -- L1：全所启用用户
                        : (u.is_enabled AND u = :me
                           OR EXISTS (SELECT 1 FROM matter_staff s
                                        JOIN matter m ON m.id = s.matter_id
                                       WHERE s.user_id = u.id AND <matter 范围谓词(user)>)
                           OR EXISTS (同构 risk_matter_staff 路径))          -- L2/L3：共现过的同事
```

- **语义**：我能把谁拉进我的案卷，取决于我本来能看见谁的案卷。L1 角色（`full_admin`/`full_operator`/`sys_admin` 之外还有 `is_admin`）等价于"同所任何人皆可加"，其余只能加与自己共现于同一宿主的人。
- **代价（已接受）**：新入职、还没进过任何案卷的同事选不到。出口有两个——由 L1 角色的人加他，或先把他加进任意一个共同宿主。不做"自助申请加入"，那会引入审批流。
- **新增接口位**：`GET /matters/{id}/selectable-users` 与 `GET /risk-matters/{id}/selectable-users`（两套路径，不引入 `/hosts/{type}/{id}`——修订稿 §1.0.2 明令禁止）—— 必须带宿主上下文，分页上限 50，不接受跨宿主批量列举。这是收窄后新出现的人员枚举探测面，裸 `/users` 列表接口第一期**不提供**（`can_manage_user` 除外，其管理页可读全所用户）。
- 与 §7.2 的当事人可见性是两套谓词，不要复用成一个"可见实体集"抽象。

## 5. `*_staff` 是权限主表

去掉组织维度后，除 L1 之外的可见性**全部**来自 `owner_id` + `*_staff` 行。它从辅助表升级成权限模型的地基：

```sql
CREATE INDEX ix_staff_user ON matter_staff (user_id, staff_role, matter_id);  -- §4 的 EXISTS 走这条，必需
CREATE INDEX ix_staff_host ON matter_staff (matter_id, staff_role);           -- 详情页/收件人解析
ALTER TABLE matter_staff ADD CONSTRAINT fk_staff_host
  FOREIGN KEY (matter_id) REFERENCES matter(id) ON DELETE RESTRICT;
```

（`risk_matter_staff` 同构一套。）

- 写入唯一入口 `StaffService`：`owner_id` 与 `*_staff(owner)` 行**同事务双写**（修订稿 §8.1 定的受控冗余）；`co_owner` / `follower` 只落 staff 表。
- 禁止绕过 StaffService 直接 UPDATE `owner_id`。
- 故障方向不对称，必须记住：**少一行** = 用户看不到自己的案子（可用性问题，会被立刻发现）；**多一行** = 用户看到了别人的案子（安全问题，不会被发现）。所以"多一行"的写入路径要有 §6 的门槛压住。

## 6. 「关注人 = 授权」的风控

v3 把这条从"可见性授权"放大成了**"读写授权"**（可见即可操作），门槛必须收紧：

| 规则 | 内容 |
|---|---|
| 谁能加/删参与人 | 仅该宿主的 `owner` 与具备 L1 数据范围的用户（§2.2 护栏 1）。协办人、关注人**不能**再往外拉人 |
| 加人前的提示 | UI 必须明写「该同事将获得查看并编辑本案全部材料（含当事人、金额、附件）的权限」——这是授权动作，不是备注 |
| 被加者条件 | `is_enabled = true` **且 `activation_status = 'active'`** **且落在操作者的可见用户集内**（§4.1，2026-09-26 收窄裁定）。第三个条件是防旁路：云之家首登自动建号但管理员未批准的 `pending` 账号，若能被加进案卷，等于绕过批准直接取得读写。在此之前写的是"无组织约束、同所任何人皆可被加"——那等于任何登录用户都能把自己没见过的案卷开放出去，与 §2.2 护栏 1 的意图相反。推论：L1 仍可加全所，L2/L3 只能加共现过的同事 |
| 禁止自我授权 | 用户不得自行往 `*_staff` 加自己（否则可枚举案号自取权限）。加人必须是他人操作或承办人变更的一部分 |
| 禁止自助提权 | `can_manage_user` 的持有者**不得修改自己的角色与数据范围**；且授予 `full_admin`（含 `unarchive`/`read_plain`）这一动作要求授予者本人已持有 `full_admin`。否则 `sys_admin` 可自我升到看全所 + 看明文 |
| 特权变更审计 | 角色/特权/数据范围调整写 `activity_log(action = ROLE_CHANGED)`，含新旧值——这是唯一允许记录范围类旧值的动作类型 |
| 移除参与人 | 移除 `owner` 必须同时改 `owner_id`（不允许无承办人）；移除 `follower` 时**连带删除其 `user_watch(follow)` 行**（§7.1） |
| 审计 | 参与人增删写 `activity_log(action = STAFF_CHANGED)`，含被授权人与操作人；**不记**当事人明文 |

## 7. 特殊实体

### 7.1 `user_watch` / 通知 —— 反向泄露通道

- 关注关系不因参与人被移除而自动失效（`favorite` 是本人行为），但 §6 的移除动作必须顺手删 `follow` 型 watch 行。
- 判为不可见时的降级（必须定，否则实现会随手选一种）：列表**保留占位行**、标题替换为「无权查看的记录」、摘要字段（状态变化、评论摘录、金额）一律不发。**不隐藏整行**——隐藏会被当成数据丢失而去追问，占位能自助解释。
- **通知只存 `event_id` + 白名单摘要，正文读取时按当前权限实时渲染**，不落渲染快照（快照会把敏感内容永久留在已失权者的收件箱里）。这是与常见通知系统做法的唯一实质分歧。
- 未读数（4.6「未读更新：3」）按**可见行**计，不按总数。

### 7.2 `party` —— 跨案件共享实体

`party` 是 PRD 1.10 的独立实体，与案件按 PRD 5.1 的 N:M 关联（同一"XX公司"一条记录被多案引用）。因此**不能**照抄宿主范围：

```
visible(user, p) = user.is_admin
  OR EXISTS (1 FROM matter_party mp JOIN matter m ON m.id = mp.matter_id
             WHERE mp.party_id = p.id AND <matter 范围谓词>)
  OR EXISTS (同构 risk_matter_party 路径)
```

即"当事人可见 = 我对它关联的至少一个宿主可见"。

- 后果：搜索客户名只命中"我有相关案件的"。第一期接受，搜索页提示"部分结果因权限未显示"，**不做全局当事人检索**。
- Party 详情页"涉及案件"逐条过滤，**总数也按可见数计**（不暴露"共 5 件"）。
- 性能：需 `matter_party (party_id, matter_id)` 反向索引；无部门索引可借，谓词按"先取用户可见宿主集再 JOIN"写。若实测慢，第一期就把当事人搜索限制为"必须带案件上下文入口"，不做独立搜索页。

### 7.3 `attachment` 与导出

- 下载：取 attachment → 按 `owner_type` 解析宿主 → 跑 §4 谓词 → 签 60s URL。不可见同样 404。禁止长效或可猜测 URL，`storage_key` 不含业务含义。
- 导出：走同一 DTO 脱敏管线，清单**逐条重判**，不信任用户已看过的列表页。第一期两档——默认脱敏导出；`can_read_plain` 才能明文导出。
- 明文查看（`can_read_plain`）记 `activity_log(action = SENSITIVE_FIELD_READ)`，含 target 与字段名，**不含值**。

### 7.4 已移除

`case_study`（案例）第一期不做，其可见性规则、发布前脱敏检查、"看到案例不等于看到源案件"的判定一并移出，留到第二期与模块同时设计。

## 8. 系统身份与自动化规则

- 规则以 `operator = SYSTEM` 执行，**绕范围但不绕只读**：可读范围限定在触发记录及其直接关联。
- 规则动作 `archive` / `assign_staff` / `update_field` 不受 §2.2 护栏 1 的"只有 owner 能改状态"约束（规则本就是代理动作），但**必须**走与人工相同的 StaffService / 状态变更服务，以保 `*_staff` 与 `owner_id` 双写一致。
- 通知模板字段白名单：`code, name, status, level, owner_name, node_name, deadline_time`。**不含** `amount / id_number / phone / description`——关注人未必该看到标的额。
- `notify` 的收件人解析后**逐个校验可见性**，不可见者静默剔除（不发"无权查看"的空通知）。

## 10. 契约测试矩阵（验收标准，PRD 原本缺"怎么算做完"）

5 角色 × 3 类对象（`matter` / `risk_matter` / `party`，其中 `party` 是跨宿主共享实体、不在 `TargetType` 内，见 §7.2）× 7 入口（list / detail / search / export / download / notification / **selectable-users**），三条全局不变量：

1. **默认拒绝**：未接 `ScopeResolver` 的宿主表查询在 CI 失败。
2. **404 一致性**：detail / download 对不可见资源一律 404，禁止任何"存在但无权"的响应形态。
3. **无旁路 + 授权闭环**：从 notification、watch feed、search、export、attachment 任一入口进入，可见集合必须与 detail 路径**完全相同**；且加/删 `follower` 后被授权者**当次请求内**即可见、移除后即不可见（§6 的回归锁）。

外加四条归属护栏与选人用例：协办人尝试改状态/换承办人必须被拒；协办人加第三人为参与人必须被拒；**L3 用户尝试把一个与自己无共现宿主的同事加为 follower 必须被拒**（§4.1 收窄的回归锁）；`selectable-users` 不带宿主上下文或跨宿主翻页必须被拒。

## 11. 裁定结论（原两项待裁定，已关闭）

| # | 议题 | 结论 |
|---|---|---|
| P-1 | 是否保留 L4 `created` + 对应角色 | **删除**。第一期不假设"录入但不办理"这类分工存在，不为凑"四级"留一档无判定内容的空转档位。范围塌缩为三档，模型与谓词同步收窄（§1/§3/§4） |
| P-2 | 三档之间是否再加档 | **不加**。L1/L2/L3 的差值已覆盖"全所 vs 我参与的 vs 我承办的"，要更细必然需要组织维度，而本期已确认不引入 |
| P-3 | 角色按什么划分 | **按功能机制**（`sys_admin` / `full_admin` / `full_operator` / `joined_operator` / `self_operator`），**不使用岗位名**。岗位到角色的映射是部署时配置，不进设计、不参与判定 |

| P-4 | 加参与人是否受范围限制（2026-09-26） | **收窄**。被加者必须落在操作者可见用户集内，定义与谓词见新增 §4.1；连带开出 `selectable-users` 接口位并限死"必须带宿主上下文" |
| P-5 | 基线"外部/访客 只读"档（2026-09-26） | **第一期不做**，列 Out of Scope（见 §1 注）。不做第四档、不为查阅场景引入功能权限点 |

| P-6 | 认证方式（2026-09-26） | **第一期双通道**：云之家登录（授权码 → eid/openId → 绑定 + 在职同步）+ 本地用户名密码。会话仍统一走服务端 `auth_session`；权限判定与通道无关。详见技术选型 §3.4 |

> 净效果：权限模型 = **3 档范围 + 4 个特权开关 + 2 条归属护栏 + 1 条选人收窄**，共 3 张身份表（`app_user` / `role` / `user_role`）+ 1 张权限主表（`*_staff`）+ 3 张认证外挂表（`app_user_credential` / `app_user_external_identity` / `auth_session`，不新增任何权限判定入口）。将来确需更细时，加 `permission`/`role_permission` 是加法变更，不返工。
