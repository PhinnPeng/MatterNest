## 候选 1 · 两条机械检查（✅ 已落地，commit `755b04e`）

`no-restricted-syntax` 两条，挂 `src/app/**`：

- **404 出口**：`fail(…, 404, …)` 只许出现在 `http.ts`（该用 `notFound()`）——
  对着第 5 条那半个：手写 404 会带出第二份「找不到」措辞，而「不可见与不存在
  **同形同措辞**」是权限模型的骨架。
- **id 形态**：`^\d{1,19}$` 与 bigint 转换只在 `http.ts:pathId()`。

两条各自做了反向红（注入 ⇒ 红 ⇒ 还原 ⇒ 绿）。lint-guard 从 4 条禁令扩到 6 条。

⚠ **落地时踩到一件事**：我给子代理的简报里断言「零基线，只有 `http.ts` 一处」，
**前提是错的** —— 那次 `grep` 静默失配（`\d` 在 ugrep 裸形态下不匹配），实际有 4 处。
子代理拒绝照做并指出矛盾，它是对的。**这条教训在 10-18 被单独立成候选**。

## 候选 2 · 修一条**恒假**的守卫（✅ 已落地，commit `755b04e`）

`docs/agents/issue-tracker.md` 上一轮刚写的守卫是 `for b in ticket/*` ——
**shell 文件名通配，不是分支通配**，仓里没有 `ticket/` 目录 ⇒ 不展开 ⇒ 逐字运行输出：

```
fatal: Not a valid object name ticket/*
✗ ticket/* 未并入
```

即**无论全并入还是一个没并入都只印同一行 `✗`**。一条恒假的门禁比没有更糟：它让人以为
这一步已经机械化了，而它本该防的第 2、3 两条事故在它眼皮底下照样能发生。

改为 `git branch --list` 枚举，并做成 `tools/branch-merged.mjs`（`pnpm branches:merged`）：
判据是纯函数、git 异常原样抛出、**扫到 0 个分支即判失败**（canary）。

⚠ **刻意不进 `pnpm verify`**：verify 在 CI 上跑，而 `actions/checkout`（无 `fetch-depth`）
只拉一个 ref ⇒ 那种工作区里 `ticket/*` 匹配 0 支，canary 会把 CI 每次跑判红。
与 `board:drift` 同类：依赖本地分支状态的守卫只能在关票那一侧手工跑。

## 候选 3 · 宿主集合单源（✅ 已落地，commit `00a0baa`）

`type-safety.md` 早写着「禁止在 `src/app/**` 里再声明一份业务枚举」，但一直没有检查。
实测清掉两处字面量（`services/selectable-users.ts`、`services/reports.ts`），
并删掉 `db/schema/hosts.ts` 里那个 **零消费者**的 `HOST_KINDS`（它的「编译期防漏」注释是假的 ——
`HostKind` 就是同文件手写的别名，只能证明字面量等于它自己）。

新增第 7 条 lint-guard 规则，两种顺序都收。

⚠ **第一版写成源码断言，而它永远不可能命中**：`stripTsComments` 的契约就是把字符串内容
一并剥掉，于是 `"matter"` 变 `""`，正则再无对象 —— 症状是**所有断言全绿、看起来仓库很干净**。
改用 AST selector 才修好。**这条教训在 10-18 被单独立成候选（否定式断言要自证）。**

## 候选 4 · revred 注入先过 `tsc`（✅ 已落地 2026-10-18）

对第 6 条：注入后若产生**编译错**，冒烟的红就不能当证据。仓里已有同性质的前置检查
（`agent-work/verify-anchors.mjs`），思路是把这类检查从「跑到库里才发现」提前到「跑之前」。

> ⚠ **落地时更正了理由**：这里原写「冒烟会因 dev server 发旧产物而**假绿**」——
> 实测不成立（见本文第 6 条的更正）。真机制是**假红**：编译不过 ⇒ 每条路由 500 ⇒
> 冒烟红 ⇒ 你以为验过了。落地产物是 `agent-work/revred-gate.mjs`
> （`tsc --noEmit` + 标出「错在你正在注入的那个文件里」），
> 并接进了本地自动循环 `_revred-loop.ps1`（那道循环只数 `red=N`，本来完全看不出来）。

**当时未落地的原因**：用户本轮选的是 1、2、5（后补 3、6），这一条没在范围内。
10-18 我自己又手工 `tsc` 了三次才发现同类问题，随后补上。

## 候选 5 · Paca 状态映射落文（✅ 已落地，commit `755b04e`）

第 1 条的根因：那四枚 status uuid **在仓里任何地方都不存在**（`grep` 全仓零命中），
于是每次读板都得重新猜，猜反一次就静默颠倒而无一处报错。

`docs/agents/issue-tracker.md` 新增该表（uuid / name / category / position），并写明：
`list_tasks` **不返回状态名**；刷新只经 MCP `list_task_statuses`（REST 协助脚本已删、不应重建）；
`list_task_statuses` 另返回 `category`；**绝不从 uuid 排序或 position 推**。

## 候选 6 · 注释承诺断言要有可 grep 的标识（✅ 已落地，commit `00a0baa`）

对第 7 条：三处注释一致写着「真库断言在 `smoke-notifications.mjs` 里」，而那份断言
**从来不存在**（三处互相印证，读起来像已经验过了）。而它按原样也**落不了地**：
冒烟只走 HTTP，`visibility()` / `canSeeHostFrom` 都是内部函数。

于是**实现它**（放在能落地的地方）：`visibility.spec.ts` 新增「② SQL 形态」——
真调 `visibility()`、把 drizzle `SQL` 对象摊成文本，断言「给不给谓词 ⇔ 无关人是否放行」
与「`*_staff` 子句只在 L2」。它与原有的内存矩阵**各守一半**：只改一侧时另一组不红。
反向红实测：把 L3 改成含 staff ⇒ ② 的两条红、① 的七条全绿。

配套进 spec（`.trellis/spec/backend/quality-guidelines.md`）：**引用别处存在的断言时，
必须写出能被 grep 到的标识**（文件 + describe/it 名）。
